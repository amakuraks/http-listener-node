## 1. Framing

The spec describes a **platform**; the repo is a **single-purpose tool**.

| Spec assumes | Repo has today |
|---|---|
| "Testing Tools" platform, many listener types | `Request Tester` — one listener, one table |
| `listeners` table with `type` + `configuration` | One Prisma model: `RequestLog` |
| `GET /api/smtp/inboxes` REST namespace | No `/api` anywhere — EJS server-rendered only |
| Nav: HTTP / SMTP / Settings | `/` redirects to `/requests` |

**Decision: restructure into a platform now** (modular monolith), rather than bolting SMTP
onto a single-purpose layout and paying for it at listener #3.

## 3. Problems found in the spec

### P1 — "Don't store attachments" + "retain raw message" cancel out

Spec §20 wants raw retained. Raw **is** the attachments, base64-encoded. A 25 MB message with
a 20 MB PDF puts 20 MB of base64 in MySQL regardless of what the attachment table says.

**Resolution:** elide attachment payloads from raw, keeping every boundary and part header:

```text
--boundary
Content-Type: application/pdf; name="invoice.pdf"
Content-Transfer-Encoding: base64
Content-Disposition: attachment; filename="invoice.pdf"

[-- 20,971,520 bytes of base64 payload elided --]
--boundary--
```

A 27 MB message collapses to roughly 15 KB with **complete structural fidelity**. The 256 KB
cap becomes a backstop for pathological input, not the primary mechanism — so in practice
almost every email is stored in full.

Rejected alternatives:

| | Why not |
|---|---|
| Naive 256 KB head cut | ~80% of stored bytes are base64 noise; closing boundary lost |
| Head 192 KB + tail 64 KB | Structure still broken, now in a confusing place |
| Full raw to filesystem | Reverses decision #6 by side effect; adds dual-write + orphan-file problem |
| Full raw in `LONGTEXT` | ~2.7 GB per 100 attachment-bearing emails; 25 MB buffered in heap |

### P2 — The `listeners` table is speculative generality

Spec §38/§48 wants it; spec §49 then says ports, cert paths and size limits come from
application config. So `configuration` is `{}`, `status` is a constant, `type` is two
hardcoded rows, and `smtp_inboxes.listener_id` is an FK to a row that never changes.

**Resolution:** drop it. The platform concept lives in the nav and URL structure, which is
where users actually experience it. Re-add it when a listener becomes runtime-configurable.

### P3 — The loopback security control breaks

`O1`/`AR-1` in [use-cases.md](../use-cases.md) rests entirely on `HOST=127.0.0.1`. But SMTP
must be reachable from other machines, and the dashboard now displays SMTP passwords in
cleartext with no login (§15 + §5.1 combined).

**Resolution:** split the bind address.

```text
WEB_HOST=127.0.0.1   <- dashboard + cleartext credentials stay on loopback
SMTP_BIND=0.0.0.0    <- SMTP reachable by test apps
```

### P4 — Spec §48's `bcc` column is always wrong

BCC by definition never appears in message headers. A `bcc` column would be permanently
empty or misleading. §19 already states the envelope is authoritative.

**Resolution:** no column. Derive it: `envelopeRecipients - (To union Cc)`.

## 4. TLS for SMTP — how it differs from a web server

The certificate is identical (same PEM pair, same X.509, same openssl). Three differences:

1. **STARTTLS is a protocol upgrade, not a port.** The connection opens in cleartext; the
   server advertises `250-STARTTLS`; the client issues `STARTTLS`; the *same TCP socket* is
   upgraded in place. The client must re-`EHLO` afterwards — pre-TLS state is discarded.

2. **TLS cannot be terminated at a reverse proxy.** The upgrade is an in-band SMTP command,
   so nginx/Caddy cannot sit in front. **Node owns the cert files directly.**

3. **The SAN must match the client's configured hostname**, not a browser URL. An SMTP client
   gives no padlock and no interstitial — it either connects or throws in your logs. Add
   `IP:` SANs too if apps connect by address.

**Client trust:** `NODE_EXTRA_CA_CERTS` (Node), `certutil -addstore -f "Root"` (Windows),
`/usr/local/share/ca-certificates/` + `update-ca-certificates` (Linux). Spec §11 is right to
prefer this over `rejectUnauthorized: false`.

**Sequencing consequence:** because decision #4 permits plaintext AUTH, **TLS is not on the
MVP critical path**. The tool works end to end with zero certificates; STARTTLS lands as an
independently testable layer.

**Views gotcha:** `app.set('views', [...])` accepts an array, so feature-local view
directories work — but only with **globally unique template names** (hence the `requests-`
and `smtp-` prefixes). EJS `include('partials/head')` resolves relative to the calling
template first, then across the array. Verify this early; it is the one piece of the
restructure that can surprise you.

## 6. SMTP ingest flow

```text
TCP :587 / :2525
  |
  v onConnect ------------------ log remoteAddress, no auth yet
  |
  v EHLO ----------------------- advertise STARTTLS (if certs loaded) + SIZE
  |
  v STARTTLS ------------------- socket upgraded in place
  |                              (skippable when SMTP_REQUIRE_TLS=false -> warn)
  v AUTH PLAIN|LOGIN --- onAuth
  |    |-- inboxService.findByUsername(username)
  |    |-- decrypt stored password (AES-256-GCM)
  |    |-- crypto.timingSafeEqual compare
  |    +-- session.inboxId = inbox.id        <- the ONLY routing decision
  |
  v MAIL FROM ------------------ envelopeFrom
  v RCPT TO -------------------- envelopeRecipients[]  (accept all, never routed on)
  |
  v DATA -- stream --+--> MailParser (streaming)
  |                  |      |-- headers, text, html
  |                  |      +-- attachment parts: drain + tally, content DISCARDED
  |                  |
  |                  +--> ElideTransform
  |                         |-- attachment payloads -> [-- N bytes elided --]
  |                         +-- 256 KB backstop cap
  |
  v stream.sizeExceeded? ------- yes -> 552, persist NOTHING
  |
  v emailService.persist() ----- single INSERT (spec §25 atomic, free)
  |    +-- throws -> 451 Temporary failure, NOT 250
  v
 250 OK
```

### Three details that decide whether this works

| | |
|---|---|
| **Use `MailParser`, not `simpleParser`** | `simpleParser` buffers the whole message. The streaming class keeps peak heap at *(text + html + 256 KB)* instead of 25 MB |
| **Drain attachment streams** | `attachment.content.resume()` — discard without buffering. Forget this and the parser stalls mid-message |
| **Check `stream.sizeExceeded` after end** | The `SIZE` advertisement is advisory; clients can lie. This flag is the real enforcement |

Peak memory per concurrent session is a few hundred KB, not 25 MB. That retires the spec §47
"SMTP must not block the dashboard" concern — but **only** on the streaming path above.

## 7. Database changes

One migration. The `requests` table is untouched.

```prisma
model SmtpInbox {
  id                Int      @id @default(autoincrement())
  name              String   @db.VarChar(191)
  username          String   @unique @db.VarChar(191)
  encryptedPassword String   @map("encrypted_password") @db.Text
  createdAt         DateTime @default(now()) @map("created_at")
  updatedAt         DateTime @updatedAt      @map("updated_at")
  emails            SmtpEmail[]
  @@map("smtp_inboxes")
}

model SmtpEmail {
  id                 Int       @id @default(autoincrement())
  inboxId            Int       @map("inbox_id")
  inbox              SmtpInbox @relation(fields: [inboxId], references: [id], onDelete: Cascade)

  envelopeFrom       String    @map("envelope_from") @db.VarChar(320)
  envelopeRecipients Json      @map("envelope_recipients")   // authoritative (spec 19)

  headerFrom         String?   @map("header_from") @db.Text
  headerTo           String?   @map("header_to")   @db.Text
  headerCc           String?   @map("header_cc")   @db.Text
  subject            String?   @db.Text
  messageId          String?   @map("message_id")  @db.Text
  headers            Json                                     // everything, verbatim

  textBody           String?   @map("text_body") @db.LongText
  htmlBody           String?   @map("html_body") @db.LongText

  rawMessage         String?   @map("raw_message")      @db.MediumText
  rawTruncated       Boolean   @default(false) @map("raw_truncated")
  rawElidedBytes     Int       @default(0)     @map("raw_elided_bytes")

  size               Int                                      // TRUE wire size, always
  receivedAt         DateTime  @default(now()) @map("received_at")

  attachments        SmtpAttachment[]

  @@index([inboxId, id(sort: Desc)])
  @@map("smtp_emails")
}

model SmtpAttachment {
  id          Int       @id @default(autoincrement())
  emailId     Int       @map("email_id")
  email       SmtpEmail @relation(fields: [emailId], references: [id], onDelete: Cascade)
  filename    String?   @db.VarChar(255)
  contentType String    @map("content_type") @db.VarChar(255)
  size        Int
  @@index([emailId])
  @@map("smtp_attachments")
}
```

### Deliberate deviations from spec §48

| Spec §48 | Here | Why |
|---|---|---|
| `listener_id` FK | removed | No `listeners` table (P2) |
| `bcc` column | removed | Always empty or wrong (P4) |
| `storage_path` | removed for MVP | No attachment content stored. Returns with enhancement #6 |
| — | `rawTruncated`, `rawElidedBytes` | Elision must be visible, never silent |
| `raw_message` | `MediumText` | `Text` is 64 KB, too small for a 256 KB cap. `LongText` is overkill |

`size` is **always the true wire size**, never the stored size — so the size limit and the UI
never lie because storage elided something.

`@@index([inboxId, id(sort: Desc)])` serves the paginated newest-first list, matching the
existing `orderBy: { id: 'desc' }` convention.

## 9. HTML rendering — the highest-risk surface

Decision #2 is "both". The safe shape:

```html
<iframe sandbox src="/smtp/emails/42/html"></iframe>
```

`src=`, **not** `srcdoc=`. With `srcdoc` the frame inherits the parent CSP and cannot be
relaxed per-frame. With `src` it is a separate response carrying its own headers:

```text
Content-Security-Policy: default-src 'none';
                         style-src 'unsafe-inline';   <- emails are all inline CSS
                         img-src data:;               <- blocks tracking pixels
                         script-src 'none';
                         frame-ancestors 'self'       <- CRITICAL, see below
X-Content-Type-Options: nosniff
```

### The one that will bite you

The global CSP in `middleware/securityHeaders.ts` sets **`frame-ancestors 'none'`**. Applied
to `/html`, that blocks *the dashboard itself* from framing it — the iframe renders blank with
a console error and no obvious cause. It **must** be overridden to `'self'` on that route.

`sandbox` with neither `allow-scripts` nor `allow-same-origin` gives the frame an opaque
origin and inert JS — belt and braces alongside the CSP.

**Escaped source stays the default tab.** Rendered HTML is opt-in, one click away.

## 10. Credential encryption

Spec §15 forces reversible encryption because the password must be displayed.

```text
plaintext --> AES-256-GCM --> iv : authTag : ciphertext --> encrypted_password
                   ^
            SMTP_CRED_KEY (32 bytes, env only - never in DB, spec 15)
```

- **GCM, not CBC** — authenticated; tampered ciphertext fails loudly instead of decrypting to garbage
- Missing or short `SMTP_CRED_KEY` -> **fail fast at boot**, matching the `required()` pattern in `config.ts`
- `crypto.timingSafeEqual` on comparison
- Password never logged, never in an error message, never in a stack trace (spec 40)

## 11. Configuration

```bash
# WEB
WEB_HOST=127.0.0.1          # renamed from HOST - breaking change, see below
PORT=3000

# SMTP
SMTP_BIND=0.0.0.0
SMTP_PORTS=587,2525
SMTP_MAX_MESSAGE_SIZE=26214400
SMTP_REQUIRE_TLS=true       # false -> plaintext AUTH permitted, logged loudly
SMTP_TLS_CERT_PATH=certs/smtp-cert.pem
SMTP_TLS_KEY_PATH=certs/smtp-key.pem
SMTP_CRED_KEY=              # REQUIRED. 32 bytes base64
RAW_MESSAGE_MAX=262144
SMTP_PAGE_SIZE=50
```

`HOST` -> `WEB_HOST` is a breaking env rename. Read `WEB_HOST ?? HOST ?? '127.0.0.1'` so
existing `.env` files keep working. This is the fix for **P3**.

`certs/` is gitignored; the operator drops cert and key there.

| At boot | Behaviour |
|---|---|
| Both cert files present | STARTTLS advertised |
| Both absent | Start without STARTTLS, warn loudly |
| Exactly one present | **Fail fast** — half a TLS config is a typo, not an intention |

## 14. Enhancements

### Accepted

| # | Enhancement | Notes |
|---|---|---|
| 1 | 301 redirects `/requests*` -> `/http/requests*` | ~10 lines. Without it every existing bookmark 404s on deploy day |
| 2 | Auto-generate credentials on Create Inbox | Random username + 32-char password. Stops `test`/`test` reaching a field the dashboard displays in cleartext |
| 3 | Search — subject / from / to (spec 36) | `LIKE` over three columns. Spec says SHOULD |
| 4 | Copy-ready SMTP config block on inbox detail | Host/port/STARTTLS/user/pass as a copyable snippet — the spec 54 acceptance flow in one click |
| 6 | Attachment content + download | `LONGBLOB` on `smtp_attachments` + `ATTACHMENT_MAX_STORE=5mb` threshold. See interaction note below |
| 8 | Live inbox refresh (SSE or 5s poll) | Watch mail arrive during an integration test run without hitting F5 |
| 9 | "Load remote images" toggle in HTML view | `/html` takes a query param and varies `img-src`. Default stays blocked |
| 11 | Port 465 implicit TLS (spec 5.3) | Cheap once STARTTLS works. **Requires a certificate** — unlike 587/2525, this port cannot start without one |

### Declined

| # | Enhancement | Why |
|---|---|---|
| 5 | `.eml` export | Lossy — elided raw means attachments are absent from the export. Reconsider alongside #6 |
| 7 | Retention policy (spec 46) | Deliberately deferred, as with the HTTP listener. Unbounded growth remains an accepted risk |
| 10 | Admin authentication (spec 5.1) | Not needed while `WEB_HOST` stays on loopback. **Becomes a prerequisite, not an enhancement, the moment it does not** |

### Interaction note on #6

Storing attachment content makes elided raw **more** correct, not less: without elision the
same bytes would be stored twice — once as base64 inside `raw_message` (~1.37x) and once as
binary in the attachment row (1.0x).

Chosen shape when #6 lands: `LONGBLOB` in MySQL with a 5 MB threshold, not filesystem storage.
The threshold removes every reason to reach for the filesystem (no 20 MB rows, no
`max_allowed_packet` risk, no heap spike) while keeping the single-storage-system invariant
that makes spec 25, 31 and 32 trivial. Filesystem plus content-addressed dedup only earns its
orphan-cleanup cost at sustained large-attachment volume.

Downloads are a new attack surface: `Content-Disposition: attachment` (never inline),
`X-Content-Type-Options: nosniff`, filename sanitised before it enters the header (a quote or
newline in `filename=` is a header-injection primitive), and `application/octet-stream` rather
than the email's declared content type.
